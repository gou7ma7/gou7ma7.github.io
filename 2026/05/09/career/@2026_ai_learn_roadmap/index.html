接下来该学什么 —— 2026 年版

本文最后更新于 2026年6月29日 早上

其实在 2024年底 我再次被裁员时候，就该彻底地重新进行职业规划，并落实。 巧合的是正好用了 2025年 一个整年尝试 AI 时代的岗位探索，终于在 2026年元旦 （以外包身份）进入一家外企，至今（本文初写作时候）碰巧半年。

最开始查了很多资料，看了很多 Roadmap，让 AI 生成了一堆，但由于没有进行深入思考，反而更加无从下手。

后来踏实做事 并 结合工作中的业务，尝试落实一些至少可以落地的方向：

  1. 空间计算 + 世界模型，大概率能成为之后的一个主流业务，就看我能提前学到多少相关技术栈了；
  2. AI Perfomance Engineering，作为我之前 DevOps 工作 AI 版，最大程度复用现有技术栈；
  3. SDK - Zephyr - RTOS - Board，通过工作日常熟悉整个生态，即使以后被开了再找工作也能有个落脚点。

0. 背景故事

CI Nightmare Flashback

从 2021年 到上海始，看了 2年 又 1年 的 CI，其间心力憔悴不值一提。

而今一封不认识的人突然发来的，让我查看我甚至没有权限的 CI 的信息，让我梦回全天随时被打断的打杂网管客服噩梦中。

居安思危，跟上时代

我维护这个博客，乃至整个学习的目的，仅仅是为了不那么快被淘汰罢了。

因为只有做到这个前提，我才能享受打游戏和单纯追求技术的快感。

现状与未来

  • 2025年上 加入百度云，以为能立足云服务商，系统地完善自己的知识体系；
  • 2025年下 加入一家号称 AI Native 的创业公司，结果只体现在对客户上。

现在的我能用上最新的大模型 + 无限量 Token，如果还学不明白，做不出个什么东西，那只能说明我不适合这个行业了。

阶段 主题 目标 内容
① Agent Eval / Test Harness 用测试开发思路切入 AI 做出一个能同时服务 DeepSeek Agent Infra、测试开发和 NVIDIA SWQA 的作品 设计 20 条真实 Agent 任务；写 runner 调模型和工具；输出 pass rate、失败原因、trace、成本、延迟
② LLM Serving / vLLM 知道模型服务怎么跑、怎么慢、怎么测 能解释 TTFT、TPOT、throughput、batch、concurrency，并能写压测报告 用 vLLM 起 OpenAI-compatible server；跑 Qwen/DeepSeek 蒸馏模型；写并发压测脚本
③ PyTorch -> CUDA 基础 从框架使用走到底层执行模型 能说清 tensor、autograd、GPU memory、kernel launch 的基本链路 写 PyTorch 推理脚本；用 profiler 看耗时/显存；写一个 CUDA vector add 或 Triton matmul 入门
④ AI Infra / Cluster Reliability 把 DevOps/SRE 经验迁移到算力平台 能定位容器、K8s、监控、故障注入中的一条完整链路 Docker/K8s 部署 vLLM；接 Prometheus/Grafana；模拟 OOM、重启、超时并写恢复策略
⑤ Coverage / Static Analysis 把传统质量工程迁移到 C/C++/CUDA 项目 看懂 Gcov、Coverity、VectorCAST 在 SDET 岗位中的位置 给一个 C++ 小项目接入 gcov/lcov；了解 Coverity 报告；把覆盖率门禁放进 CI

第一件事：不要先读 CUDA，也不要先堆框架。先新建一个 ai-agent-eval-harness 小项目，只做一件事：把 10 条“能明确判定成功/失败”的 Agent 任务写成 tasks.jsonl，再用一个 Python runner 调模型跑完，生成 reports/run-001.md，里面至少包含 pass_rate、失败样例、token 成本和耗时。

1. 先做 Agent Eval / Test Harness

这一阶段的目标不是“学会一个评测框架”，而是做出一个可以拿去面试讲的作品：

我把过去 DevOps / 测试开发 / 研发效能平台的经验，迁移成了一套 Agent 测试与回归评测系统。它能把真实工作任务写成数据集，自动调用模型和工具执行，记录 trace、成本、延迟和失败原因，并在 CI 中给出 pass/fail 门禁。

这个作品同时服务三个求职方向：

  1. DeepSeek Agent Infra / Agent Harness / 测试开发：证明我理解 Agent 运行器、工具调用、状态记录、失败恢复和评测闭环。
  2. NVIDIA SWQA / SDET / DGX Cloud Test：证明我能把非确定性的 AI 系统做成可回归、可观测、可报告的质量工程。
  3. 我自己的职业迁移：把原来的 CI/CD、测试平台、Grafana/Prometheus、质量门禁经验，转译成 AI 时代的工程语言。

1.2 第一版只做这 4 个能力

不要一开始就接 LangGraph、RAG、MCP、vLLM、K8s。第一版只做 4 个能力。

能力 1：任务数据集

把 Agent 任务写成 JSONL。每一行是一条可重复执行的测试用例。

为什么用 JSONL：因为它天然适合“每行一个样本”，以后可以直接接 Promptfoo、Inspect AI、OpenAI Evals、批处理任务或 CI 产物。

能力 2：最小 Agent Runner

先别写复杂 planner。第一版 Agent 只需要：

  1. 读取一条 task；
  2. 组装 prompt；
  3. 调一次模型；
  4. 要求模型返回结构化 JSON；
  5. 调 scorer；
  6. 写 trace；
  7. 更新报告。

第一版可以不做多工具调用。先让它像一个“AI 测试执行器”。等 10 条任务跑通，再加工具。

能力 3：可解释评分

不要只写 pass/fail。每条任务至少输出：

第一版评分器按优先级分三类：

  1. schema_score：结构是否满足要求，比如必须有 matched_skills、gaps、next_actions。
  2. keyword_score：是否覆盖关键事实，比如 Python、CI/CD、Kubernetes、Agent Infra。
  3. judge_score：后续再加，让另一个模型评估回答质量。

一开始只做前两类，因为它们确定、稳定、便宜，最像传统测试。

报告给人看，trace 给工程师排查。

这就是你过去做 DevOps/测试平台的优势：别人只会说“模型效果不错”，你能说“这次回归通过率 70%，失败主要集中在输出 schema 不稳定，平均延迟 4.2 秒，成本 0.12 美元”。

1.3 先设计 20 条真实 Agent 任务

20 条任务不要编得太学术，要贴近你自己的经历和目标岗位。建议分成 5 组，每组 4 条。

A. 职业匹配类

目标：服务 DeepSeek / NVIDIA 投递，也展示你会做信息抽取、结构化分析和评测。

  1. 给一份简历和 NVIDIA SDET JD，输出匹配项、短板、学习计划。
  2. 给一份简历和 DeepSeek Agent Infra 岗位，输出匹配项、短板、项目建议。
  3. 给三份岗位 JD，按匹配度排序并解释理由。
  4. 给一段招聘海报 OCR 文本，提取岗位列表并归类。

评分重点：

  1. 是否输出固定 JSON schema；
  2. 是否引用简历中的真实经历；
  3. 是否区分“强匹配、部分匹配、短板”；
  4. 是否给出可执行 next actions。

B. 代码与仓库任务类

目标：服务 Code Agent / Agent Harness / 测试开发岗位。

  1. 给一个 Python 函数和失败测试，要求定位 bug 并给出修复 patch。
  2. 给一个小仓库目录结构，要求判断应该先读哪些文件。
  3. 给一段 CI 失败日志，要求总结 root cause 和修复建议。
  4. 给一个 PR diff，要求输出 code review findings。

评分重点：

  1. 是否定位到正确文件或函数；
  2. 是否能解释失败原因；
  3. 是否给出最小修复；
  4. 是否避免无关重构。

C. 运维与可靠性任务类

目标：服务 NVIDIA DGX Cloud Test、DeepSeek AI 平台运维、算力集群可靠性岗位。

  1. 给 Prometheus 告警和服务日志，要求判断故障方向。
  2. 给 Kubernetes Pod OOM 事件，要求给排查步骤。
  3. 给一次 CI flaky test 记录，要求判断是否应重跑、隔离还是修复。
  4. 给延迟升高的 trace 摘要，要求找瓶颈。

评分重点：

  1. 是否按层次排查：应用、容器、节点、网络、依赖；
  2. 是否给出可验证命令；
  3. 是否区分临时止血和长期修复；
  4. 是否输出风险和回滚方案。

D. Agent 工具调用类

目标：逐步从“单次 LLM 调用”升级到“真正的 Agent”。

  1. 让 Agent 调用 read_file 工具读取简历摘要，再回答岗位匹配问题。
  2. 让 Agent 调用 search_notes 工具从本地 markdown 中找学习记录。
  3. 让 Agent 调用 run_shell 工具执行一个安全命令并总结输出。
  4. 让 Agent 在工具失败时重试或降级处理。

评分重点：

  1. 是否选择了正确工具；
  2. 是否传了正确参数；
  3. 是否正确使用工具结果；
  4. 工具失败时是否胡编。

E. 数据质量与评测类

目标：服务 DeepSeek Code Agent 数据工程师、Agent Harness、预训练/后训练数据协作。

  1. 给 10 条任务样本，要求找出无法自动判分的样本。
  2. 给一条模糊 expected，要求改写成可测试标准。
  3. 给失败输出，要求归因到 prompt、模型、工具、数据还是 scorer。
  4. 给两版 prompt 的结果，要求判断哪版更适合进 CI。

评分重点：

  1. 是否能识别不可判分样本；
  2. 是否能把模糊需求改成明确断言；
  3. 是否能做失败归因；
  4. 是否能给出评测集改进建议。

1.5 技术选型

第一版自研，不直接上大框架。理由很简单：自研能逼自己理解最小闭环。

模块 第一版 第二版
任务格式 手写 JSONL Promptfoo / Inspect AI dataset

1.6 相关资料链接

先按这个顺序看，不要同时开十个坑。

  1. Promptfoo Intro：理解“LLM 应用也应该测试驱动开发”，后续可以把 JSONL 数据集迁进去。
  2. Promptfoo CLI：学习如何从命令行跑 eval，以及如何接 CI。
  3. Inspect AI：看它如何把 dataset、agent、tool、scorer 拆成可组合模块，尤其适合 Agent 任务。
  4. Inspect Evals：看看真实世界 benchmark 如何组织任务和评分。
  5. OpenAI Evals API Reference：理解官方 eval 对“数据源、测试标准、grader、run”的抽象。
  6. OpenAI Structured Outputs：学习如何强制模型输出稳定 JSON schema。
  7. Langfuse Observability：第二版接入，用来记录 LLM 调用、成本、延迟和调试 trace。
  8. OpenTelemetry Traces：理解 trace/span 的通用概念，避免只会用某个 LLM 平台。
  9. GitHub Actions Documentation：后续把 eval 变成 PR 门禁。
  10. pytest Documentation：你的第一版 schema/scorer 测试直接用它。

1.8 不要做什么

第一版先不要做这些事：

  1. 不要先接复杂前端；
  2. 不要先写 LangGraph；
  3. 不要先研究 CUDA；
  4. 不要先接十个模型；
  5. 不要让 LLM judge 成为唯一评分器；
  6. 不要把任务写成“请总结一下”这种无法判分的开放题；
  7. 不要追求 100% 自动化，先保证每个失败都能解释。

你现在最需要的是一个能证明迁移能力的作品，不是一个巨大的玩具系统。
